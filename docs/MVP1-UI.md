# MYATOM MVP1 界面与交互设计（v0.1）

状态：MVP1 实施设计，2026-10-30。范围以 [PRD](PRD.md) 的 MVP1 为准，状态、命令与持久化以 [系统架构](ARCHITECTURE.md) 为准，冲突处理遵循 [ADR-002](decisions/ADR-002-change-control.md)。Atoms 平台验证证据保存在本机 `D:\AI\ATOM笔试\docs\ATOMS-SPIKES.md`；本设计不把尚未取得的证据写成平台事实。

## 1. 设计目标与边界

用户从一句想法开始，能够辨认当前需要自己做什么、Agent 正在做什么、哪些结果已经真实保存。MVP1 的最终可见结果是**代码版本、构建与测试结果、可恢复的项目**。生成应用的交互预览及其业务数据持久化属于 MVP2；在 `PreviewGateway` 尚未接通时，界面不得用截图、假 iframe 或模拟成功状态冒充预览。

本设计只细化已确认的三栏布局和预定义卡片，不引入完整 A2UI/AG-UI 协议。卡片显示为服务端状态的投影；按钮是否可执行由服务端阶段、卡片版本和用户身份再次校验。前端拦截和禁用态只用于减少误操作。

### 探索过的呈现方式

| 方式 | 优点 | 主要代价 | 决定 |
| --- | --- | --- | --- |
| 全屏向导 | 每步专注 | 构建日志与旧决策难回看，恢复后定位困难 | 不采用 |
| 对话 + 决策工作台 + 版本侧栏 | 对话保留上下文，关键确认有明确门禁，产物有固定位置 | 需按阶段分配桌面空间，避免空侧栏压缩当前任务 | **MVP1 采用** |
| 仿 IDE 多面板 | 文件查看方便 | 对非技术用户过重；容易掩盖澄清和确认 | 留待后续按证据评估 |

## 2. 页面与信息结构

### 项目入口 `/`

- 顶部一句价值说明：“描述你想做的网页应用，确认计划后开始生成。”主按钮“创建项目”；不给用户暗示已经完成云部署。
- 最近项目列表按最近更新时间排序。每项只显示项目名、最后阶段、更新时间、最近成功版本（如有）和“继续”操作。无项目时显示一个简短示例需求，点击只填入输入框，不自动提交。
- 创建流程先提交 `POST /api/projects` 得到项目 ID，再提交本次需求到 `POST /api/projects/{id}/runs`。请求中采用稳定幂等键；提交期间按钮禁用并保留原文。失败可重试，不能在 UI 上虚构项目已创建。
- 访客身份使用服务端签发的凭证；项目 URL 可分享/收藏，但 URL 中的可猜测 ID 不等于访问权限。失去凭证时给出“无法验证该项目的访问权限”，不能静默新建一个同名空项目。

### 项目工作台 `/projects/:projectId`

```text
┌──────────────────┬──────────────────────────────────┬──────────────────────────┐
│ 项目列           │ 决策与构建时间线                 │ 版本与结果               │
│ 项目列表 / 新建  │ 项目标题 + 当前阶段/状态          │ 已保存版本               │
│ 当前项目高亮     │ 需求原文                         │ 文件摘要 / 测试结果      │
│ 最近版本标记     │ 澄清卡 → 计划卡 → 进度 → 结果     │ 预览入口状态             │
│                 │ 底部输入与当前可执行动作         │                          │
└──────────────────┴──────────────────────────────────┴──────────────────────────┘
```

- 桌面宽屏建议左列 224–256 px，中列最少 560 px 且优先获得宽度，右列 300–360 px。不要为容纳三列让确认卡窄到难编辑。
- 2026-10-31 用户已取消 MYATOM 建造工作台的移动端适配。MVP1 设计与验收以 1280×720、1366×768、1440×900 的桌面浏览器为主；更窄视口不承诺专用页签或完整流程。无结果时可收起右区，保证**当前待用户处理的卡片**获得主要空间。
- 顶部固定显示项目名、`run` 状态、最近保存时间和连接状态。`已保存`只在服务端写入确认后出现；`正在同步`与`连接中断`必须可区分。
- 时间线按事件 `seq` 排列，包含用户需求、决策卡、阶段事件和结果卡。当前需要操作的卡片展开，已结束的卡片折叠但可读；不自动滚走用户正在编辑或查看的内容。
- 右侧在没有版本时显示“尚无生成版本”；有版本时展示版本号、生成时间、文件数量/变更摘要与真实测试报告。源码文件可下载/查看时再显示入口。交互预览入口只在服务端返回有效 `preview_ref` 且环境允许时启用；否则写明“交互预览将在 MVP2 接入”。

## 3. 默认视觉语言与组件

默认主题取“**编辑台**”方向：暖白底、墨色正文、铜橙用于需要用户决策的操作、深青用于已完成状态。阶段编号与版本号用等宽数字；卡片像有明确标题和脚注的工作记录。避免大片渐变和聊天气泡堆叠，使评审一眼看到“待确认”与“真实结果”的区别。MVP4 的二次元主题复用相同布局、语义 token 与交互，主题切换不改业务逻辑。

建议先定义 `surface`、`surface-raised`、`text`、`text-muted`、`border`、`accent-action`、`success`、`warning`、`danger`、`focus` 等 CSS 语义变量，不让组件写死颜色。正文优先清楚可读的中文字体回退栈，代码/版本号采用等宽回退栈；不依赖在线字体加载。状态不能仅靠颜色表达，配文字和图标。动画限卡片进入、状态切换和进度脉冲，尊重 `prefers-reduced-motion`；没有“百分比进度”，除非服务端提供真实可计量总量。

通用卡片头包含：类型、状态、更新时间、`run`/版本识别信息；正文是类型化字段；底部动作区只显示此阶段允许的动作。错误文案格式为“发生了什么 → 是否保存 → 下一步”。所有输入有可见标签、错误提示和字符计数；确认动作在键盘焦点顺序内，焦点环清晰。

## 4. 核心卡片与动作

### 4.1 需求澄清卡

1. **已知**：从用户输入提取的目标、目标用户、核心动作；用户能看到原需求全文。
2. **待确认假设**：每条显示默认值及影响。没有假设也明确写“暂无需要确认的假设”。
3. **关键问题**：最多三题，说明为何需要、建议默认值、回答控件。问题可为单选或短文本；不以自由聊天替代结构化答案。

主动作“确认这些需求”；次动作“修改原需求”。用户可留空且接受默认值的题须显式勾选/选择默认值；关键约束缺失时不能确认。提交 `card_id`、`spec_version`、答案和幂等键；成功后卡片锁定并显示已提交摘要。服务端拒绝过期版本时保留本地编辑，显示“计划已更新，请核对后再提交”，加载最新卡片并让用户比较，不能自动覆盖回答。

### 4.2 Build Plan 确认卡

按“将做什么 / 如何存数据 / 如何验收”组织，而不是展示未解释的 Agent 思维链：

- 页面与流程：页面清单，每页的关键输入、动作和结果。
- 功能范围：将实现项与本轮不实现项分列；对模板不支持的需求给出可见限制。
- 数据模型：实体、关键字段、是否持久化；和验收任务能对上。
- 技术方案：固定 React + TypeScript + Vite 模板及受控数据接口；只展示用户关心的约束，不让用户随手改成另一技术栈。
- 验收点：可观察的操作和期望结果；估计耗时/成本若没有可信数值，显示“待运行估计”，不捏造金额或完成时间。

主动作“确认并开始生成”，次动作“修改计划”“返回澄清”。编辑采用分区表单，保存草稿不触发代码生成；用户提交修改后服务端重新生成/校验计划并增加 `spec_version`，用户必须确认最新版本。确认前任何写文件或构建状态均不应出现。确认按钮的上下文写明“确认后开始消耗模型额度”，并以 `approved_spec_version` 显示已批准的不可变版本。

### 4.3 构建进度卡

阶段顺序与架构 Node 对齐：准备模板 → 编写代码 → 构建与测试 → （必要时）诊断修复 → 保存版本。每项显示 `等待 / 进行中 / 已完成 / 失败 / 已取消`、服务端时间戳、耗时与简短结果。`CodeLoop` 只展示当前任务与已完成任务数；不展示模型私有推理。修复时写清“第 1/2 轮修复”和触发的真实错误类别。

可展开的详情显示文件变更摘要、脱敏日志片段、模型调用/预算摘要和 `trace_id` 复制动作。取消按钮调用服务端取消命令；按钮按下后先显示“正在取消”，收到最终状态才显示“已取消”。连接断开时显示“进度更新中断，任务可能仍在运行”，提供“重新连接”和“刷新状态”，不得把断线当失败，也不得重新提交 run。

### 4.4 测试结果卡与版本

独立列出模板构建、类型检查、自动化测试、浏览器检查（若未运行标“未执行”）及每项实际状态、耗时、日志/证据入口。总状态只能由实际命令结果归纳，不能因文件存在就标成功。成功时显示不可变版本 ID、文件摘要和下一步；失败时显示主要错误、定位文件/命令、已尝试修复轮数及“重试 / 回到计划 / 查看上一成功版本”中当前有效的操作。若没有上一成功版本，不渲染该入口。

`Package` 成功但 `Preview` 未就绪时，明确分开“代码已保存”和“预览未可用”。旧版本可查看但不声称回滚业务数据。结果卡的“测试通过”只表示执行过且通过的项目，绝不等同最终在线 Demo 验收。

## 5. 页面状态与恢复

| 服务端阶段/状态 | 主区重点 | 输入区与操作 | 右区 |
| --- | --- | --- | --- |
| 无项目 | 创建项目表单 | 可提交需求 | 空说明 |
| Intake / Clarify 运行中 | 真实阶段和最近事件 | 禁止重复提交，可取消 | 尚无版本 |
| WaitClarify | 澄清卡置顶 | 回答、改原需求、确认 | 尚无版本 |
| Plan 运行中 | 计划生成状态 | 等待、可取消 | 尚无版本 |
| WaitPlan | 最新计划卡置顶 | 编辑、返回、确认 | 尚无版本 |
| Prepare / CodeLoop / BuildTest / Diagnose / Package | 构建进度，真实事件 | 禁止改变已确认 spec；可取消 | 最后好版本仍可查看 |
| Done | 测试结果与保存版本 | 新修改需求创建新 run | 当前及历史版本 |
| NeedsUser / 失败 / 预算停止 | 具体原因、已保存内容和可行动作 | 按服务端允许动作重试或改需求 | 最后好版本 |
| 已取消 | 停止点、已保留记录 | 新 run 或有效重试 | 最后好版本 |

刷新、重进或标签页恢复时：先从 `GET /api/projects/{id}` 取服务端项目与活动 run；再按记录的事件游标请求 `GET /api/runs/{id}/events?after_seq=n`，按 `seq` 去重，并取最新决策卡/版本状态。事件游标只是性能优化，卡片最终状态以服务端当前快照为准。若浏览器仅保留项目 ID 而服务器找不到，显示明确的“项目不存在或无权访问”及回首页动作。等待确认态恢复后仍可编辑；构建态恢复后只观察同一个 `run_id`。MVP1 可以通过有界轮询更新事件；SSE、心跳与断线补齐在 MVP2 完整落地，前端保留相同事件 reducer。

网络断开时保留当前草稿并标记未提交。恢复后先同步服务端卡片版本再允许提交；409 冲突时展示最新内容和本地草稿，不自动重放确认。服务端 429/超时/预算停止时，区分“服务正在自动重试”“本轮已停止”“需要用户调整计划”，避免用户重复点击造成新运行。

## 6. 卡片与前端实现契约

按 [PRD §4](PRD.md#4-界面与结构化呈现) 使用 `type`、`schema_version`、`card_id`、`run_id`、`status`、`payload`、`actions`。MVP1 仅注册 `clarification`、`build_plan`、`build_progress`、`test_result` 四种渲染器；以后新增图表/架构图可用受限 schema 插入时间线（MVP3），不能让模型注入 HTML。未知类型显示标题、时间与安全纯文本摘要，并提供“查看原始结构化信息”下载，不执行脚本。

前端每个动作都带 `card_id`、当前 `spec_version`、动作类型与稳定幂等键。用户双击、浏览器自动重试或返回后重放时应得到同一个服务端结果；API 返回 409 时重新加载当前状态。按钮禁用逻辑从 `actions` 与服务端阶段派生，不能只凭本地 UI 路由。日志和卡片字段按纯文本渲染，长输出折叠，密钥及预览业务数据不得写入浏览器活动流。

## 7. MVP1 设计验收与 TC 维护

每个用例记录输入、预期、实际、环境、构建版本和截图/事件证据。前端改动同步更新相关用例，重点覆盖 1280×720、1366×768、1440×900 桌面视口、键盘流程和无障碍标签。

| TC | 场景与期望 |
| --- | --- |
| UI-01 | 新访客创建项目，空需求/过长需求有明确错误；成功后项目入口可再次找到项目。 |
| UI-02 | 澄清卡最多三题，默认值需显式接受；关键问题未答不能确认。 |
| UI-03 | 修改计划产生新 `spec_version`；旧卡确认返回冲突，显示新旧内容且不写文件。 |
| UI-04 | 生成中刷新后仍显示同一个 `run_id` 和真实阶段；没有第二个构建。 |
| UI-05 | 网络中断后保留未提交答案，恢复时核对版本；事件按 `seq` 去重。 |
| UI-06 | 构建失败展示错误、实际测试状态与有效动作；成功版本不会被失败 run 覆盖。 |
| UI-07 | 无 `preview_ref` 时无可点击交互预览；代码保存与预览就绪状态分开。 |
| UI-08 | 桌面目标视口下待确认卡易找、可键盘完成；状态有文字，减少动态效果偏好生效。 |

MVP1 退出检查：评审能完成“创建项目 → 澄清 → 编辑并确认计划 → 查看真实生成与测试 → 刷新恢复版本”；`TC-BE-01/02` 对应的前端门禁和重复提交也能在界面上验证。完整交互预览、生成应用数据持久化和在线链接依照 [PRD §6](PRD.md#6-分期与验收) 在后续阶段验证，不能把 MVP1 的界面截图当作这些能力的证据。
