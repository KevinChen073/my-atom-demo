# MYATOM 设计标准与页面原型（v1.1，早期探索记录）

状态：早期探索记录，2026-10-31。**主工作台布局与切换行为以用户最新确认的 [工作台视觉方向 v2](WORKBENCH-V2.md) 为准**；本文中“等待决策时扩大为主要区域、收起预览、三列平均分配”等探索不再作为实施要求。视觉 token、卡片状态和无障碍原则仍可参考本文。产品边界以 [PRD](PRD.md)、[架构](ARCHITECTURE.md) 和 [MVP1 界面契约](MVP1-UI.md) 为准；若未来修改这些已确认边界，遵循 [ADR-002](decisions/ADR-002-change-control.md)。[首张风格图](../design-prototype/visual-direction-v1.png) 与 [可点击视觉原型](../design-prototype/index.html) 主要探索“澄清”阶段，不代表最终整体工作台布局，也不连接模型、数据库或真实预览。MYATOM 建造工作台取消移动端适配；旧图中的手机插图不再属于目标设计。

## 1. 设计命题

用户在每个阶段只需回答一个问题：**现在需要我做什么？系统已真实完成什么？** 页面围绕这个判断组织，不把 Agent 的所有输出平铺成等权卡片。

主用户是有想法但不一定会写代码的人；评审还要验证真实生成、真实测试、持久化与最终在线预览。因此首页应让人立即开始描述应用，工作台应让用户先处理当前决策，完成后再把空间交给真实预览。步骤、日志、代码、额度等是可查证的辅助信息，不抢占主视线。

### 1.1 三种方向与取舍

| 方向 | 适合之处 | 主要问题 | 决定 |
| --- | --- | --- | --- |
| 全屏分步向导 | 澄清与确认非常聚焦 | 用户看不到“对话生成应用”的主体体验；产物和历史难回看 | 只借用其决策聚焦 |
| 常见的对话 + 预览工作台 | 一眼像应用生成器；生成和成果可同时观察，迭代顺手 | 预览未就绪时容易出现空半屏；长对话会冲淡关键确认 | 保留为整体骨架 |
| **对话 + 预览骨架，决策态聚焦** | 生成/预览时保持行业熟悉的双区；需要确认时扩大当前卡片并暂收预览 | 需处理面板切换、草稿和焦点恢复 | **推荐，待视觉确认** |

原风格图把“澄清卡”呈现成几乎整页的表单，适合说明一个重要门禁，却不能代表整体产品。整体工作台应保持项目导航、对话/活动流、预览/结果的熟悉关系；澄清与计划等待确认时让卡片短暂成为主角。三块区域是信息架构，不是始终平均分配的等宽列。真实预览在 MVP2 可用后获得主要面积。

### 1.2 可核对的参考

| 产品 | 可借鉴的具体行为 | MYATOM 的取舍 |
| --- | --- | --- |
| [Atoms：Working with Agents](https://help.atoms.dev/en/articles/12129548-working-with-agents)、[App Viewer](https://help.atoms.dev/en/articles/12129554-app-viewer) | 工作步骤、问题卡、计划卡、版本卡以及可操作预览串在同一旅程；预览有桌面/手机检查入口 | 保留决策门禁与版本可试性；不复制多 Agent 人设和界面装饰 |

以上是对公开产品文档的设计推论，不宣称这些产品的所有登录后页面布局与 MYATOM 相同。

## 2. 信息架构与页面清单

```text
首页 /
  ├─ 创建项目 → 提交需求
  └─ 最近项目 → 继续
工作台 /projects/:id
  ├─ 当前任务：澄清 / 计划 / 构建 / 结果
  ├─ 过程：需求原文、历史决定、事件
  ├─ 产物：已保存版本、测试、文件；MVP2 起可用预览
  └─ 项目导航：列表、新建、返回首页
```

首页和工作台是两种不同任务：首页负责开始；工作台负责推进与验证。工作台右侧的内容依赖阶段，不在空项目时堆叠“版本”“测试”“文件”“预览”四个空卡片。

### 2.1 各阶段的屏幕主角

| 阶段 | 首屏必须看到 | 次级内容 | 默认收起/不出现 |
| --- | --- | --- | --- |
| 首次进入 | 一句话价值说明、需求输入、单一主按钮、一个示例 | 最近项目 | 功能宣传卡、无意义统计 |
| 等待澄清 | 问题、默认建议、影响、确认按钮 | 原始需求、已知条件 | 空版本区、完整事件流 |
| 等待计划 | 可理解的页面/数据/验收摘要、修改与确认 | 技术模板、限制说明 | 模型长推理、日志 |
| 生成中 | 当前阶段、最近真实事件、取消动作 | 已完成步骤、最后可用版本 | 虚构百分比、持续跳动的假日志 |
| 生成结束 | 真实结果、版本号、测试证据、下一步 | 文件列表、日志 | 未执行项目的“通过”字样 |
| MVP2 预览就绪 | **可交互应用预览**、版本和视口切换 | 对话/迭代输入、测试摘要 | 展开状态的长时间线 |

## 3. 页面原型与视口分配

MYATOM 建造工作台按 1280×720、1366×768、1440×900 桌面浏览器设计与验收，不再设计手机专用界面。尺寸是设计起点，实际以容器和内容验证。所有主要动作应在首个可视区域内，长内容用局部展开或自然滚动，不能为了凑首屏截断关键说明。

### 3.1 首页

```text
┌─ MYATOM ───────────────────────────────────── 最近项目 ───────┐
│                                                               │
│  把一个想法，做成能使用的网页。                                  │
│  描述用户要完成的事；确认计划后开始生成。                        │
│                                                               │
│  你想做什么应用？                                                │
│  ┌───────────────────────────────────────────────────────┐    │
│  │ 例如：做一个可记录每周支出的工具……                      │    │
│  └───────────────────────────────────────────────────────┘    │
│  项目名称（可选）                           [创建并开始 →]      │
│  试试示例需求                                                  │
└───────────────────────────────────────────────────────────────┘
```

主文案和输入区占中间偏左 720px 左右。最近项目只显示 3–5 个，优先让回访用户继续；超出部分进入项目列表。示例只填入输入框，不自动提交。首页不展示尚未具备的“云发布”“一键上线”承诺。

### 3.2 工作台：等待用户决策

```text
┌ 项目导航 224 ┬────────────── 当前决定 ≥680 ──────────────┬ 证据 280* ┐
│ MYATOM        │ 项目名 / 待确认 / 已保存时间                 │ 摘要        │
│ + 新建        │ 需求 → 澄清 → 计划 → 生成 → 验证             │            │
│ 最近项目      │                                            │ *无版本时： │
│              │ 01  需求澄清 / 请先回答这 2 个问题          │ 仅一句说明  │
│              │ 已知目标（两行摘要）                        │ 或整区隐藏  │
│              │ 问题 1 + 建议值 + 影响                      │            │
│              │ 问题 2 + 建议值 + 影响                      │            │
│              │ [修改需求]              [确认这些需求 →]     │            │
│              │                                            │            │
│              │ 已完成的记录（折叠）                        │            │
└──────────────┴────────────────────────────────────────────┴────────────┘
```

桌面左导航 208–232px，可折叠为 56px；主内容最大 820px，阅读文字列 640–720px。等待决策且尚无结果时，右区默认收起，主区居中并获得剩余宽度。已有上一成功版本时右区 280–320px 展示“上一可用版本”，但不可压缩当前确认卡到 680px 以下；不足则改抽屉。顶部 64–72px，避免占去笔记本首屏。主动作固定在当前卡的尾部，用户滚读完内容即看到；不把确认按钮脱离上下文悬浮到页面角落。

### 3.3 工作台：生成中与结果

生成中主区只展开当前步骤和最近 3 条事件；全部步骤和日志在“查看过程”中展开。结果页以“**代码已保存 / 构建通过 / 预览未接入**”等独立事实开头，再列具体检查。结果右区展示版本、文件与预览入口状态。失败时保持上一成功版本可见，失败 run 不替换它。

MVP2 预览就绪后采用两区：左侧对话/迭代 380–440px，右侧预览占其余宽度且最少 640px。用户选“代码”或“测试”时才替换预览视图。等待确认时可暂收预览，让卡片有足够空间；确认结束后恢复预览及原浏览位置。切换不丢表单草稿。

### 3.4 桌面工作区的状态变化

同一桌面骨架有三种空间分配：等待澄清/计划时扩大决策区；生成中显示对话与真实进度，右侧保留最后可用版本或收起；预览就绪时右侧成为主角，左侧保留继续迭代的输入。位置保持稳定，让用户理解这是同一个项目的连续过程。

## 4. 交互契约

### 4.1 一条任务、一个主动作

- 首页：“创建并开始”；澄清：“确认这些需求”；计划：“确认并开始生成”；成功：“查看版本/预览”（按实际可用能力）；失败：“查看原因”或“重试”。同屏只有一个高强调按钮。
- 页面状态来自服务端阶段和卡片 `actions`。前端禁用只做即时反馈，服务端再次校验 `card_id`、`spec_version` 与幂等键。
- 已处理的决策卡转为只读摘要，保留“谁在何时确认、确认版本”，避免在长时间线里重复呈现完整表单。
- 用户主动滚动查看历史时，新增事件只更新“有新进展”提示，不强制把视口拉到底部。

### 4.2 澄清卡

上方 1–2 行已知目标；每次最多三题。每题依次是问题、为何需要、推荐值、控件。推荐值必须被用户明确选中或接受，不能因为输入框空着就当默认已确认。必填题未完成时主动作禁用，同时在题目旁提示原因。修改原需求时保留原文，提交后进入重新澄清；旧卡不能继续确认。

### 4.3 计划卡

默认只显示“将做什么、如何存数据、如何验收、限制”四段。页面和验收点可逐项扫描；技术栈详情折叠但注明固定模板。修改计划用可编辑反馈或分区编辑，更新计划后需重新确认最新版本。确认前明确提示开始模型与构建消耗。拒绝过期版本时保留草稿并提供“比较最新版”，不能静默覆盖。

### 4.4 构建与测试

阶段只有“等待/正在做/完成/失败/取消”真实状态；无可计量总量时不显示百分比。修复循环显示第几轮与上限。连接断开时用“进度暂时无法更新，任务可能继续运行”，提供重新连接，不能自动创建新 run。测试结果列出已执行和未执行；成功/失败文案后紧跟版本或原因与下一步。原始日志默认折叠，最多先展示摘要和可复制的 `trace_id`。

### 4.5 预览与版本

MVP1 只在实际源码版本存在时展示版本；无 `preview_ref` 则显示“交互预览尚未接入”，不得放可点击但无效的按钮。MVP2 的预览必须能点击和输入，提供重新载入与在新窗口打开；生成应用的手机视口检查可按该应用需求另行加入，不属于 MYATOM 建造工作台的移动端适配。切换版本时明确提示正在查看历史版本。预览里的业务数据刷新读回才可标“持久化已验证”。代码版本回退与业务数据回退分别描述。

### 4.6 状态文案模板

| 状态 | 文案结构与示例 |
| --- | --- |
| 空 | “还没有生成版本。确认计划后，版本和测试结果会出现在这里。” |
| 加载 | “正在读取项目…”；骨架仅覆盖真实将出现的区域，不铺满整页 |
| 错误 | “构建未通过：类型检查发现 2 个错误。项目与上一个版本已保存。查看错误或修改计划。” |
| 离线 | “进度更新中断；任务可能仍在运行。重新连接后会继续读取同一次运行。” |
| 冲突 | “计划已有新版。你的编辑仍在本页，请比较后重新确认。” |
| 成功 | “代码版本 v3 已保存。构建与类型检查通过；浏览器检查尚未执行。” |

## 5. 视觉系统

默认主题名“编辑台”。暖纸色、深墨绿和克制的陶土橙，像一份可认真审阅的工作记录。主界面依靠文字层级、行距与留白建立结构；不使用蓝紫渐变、发光圆球、彩色数据卡矩阵或无意义插画。品牌元素仅在首页与导航出现，进入工作台后弱化。

### 5.1 Token（CSS 语义变量）

| 用途 | 值 | 说明 |
| --- | --- | --- |
| `--bg` | `#F5F4EF` | 全局底色 |
| `--surface` | `#FFFEFA` | 当前任务及表单 |
| `--surface-soft` | `#EEEFE8` | 次级摘要 |
| `--ink` | `#172522` | 主文字 |
| `--ink-muted` | `#53635C` | 次级文字；避免过浅灰 |
| `--line` | `#D5DCD4` | 仅用于分组边界 |
| `--action` | `#A64B2B` | 待用户决策的主动作 |
| `--action-hover` | `#853A21` | 主动作悬停 |
| `--success` | `#245F52` | 已完成与可用版本 |
| `--warning` | `#8A4C1E` | 需注意 |
| `--danger` | `#A43D34` | 失败 |
| `--focus` | `#2A6D61` | 键盘焦点 |

空间尺度：`4, 8, 12, 16, 24, 32, 48, 64px`；卡内间距 24px，段间 24–32px，控件间 8–12px。卡片圆角 10–12px、按钮 8px、状态胶囊 999px；阴影仅用于抽屉/悬浮层，普通卡片用浅边界或底色区分。图标用同一套 1.5–2px 线宽；能用短文字说明时不加图标。

### 5.2 字体与密度

- 首选字体组合：中文 `PingFang SC / Microsoft YaHei / Noto Sans CJK SC / system-ui`；英文与数字沿用系统无衬线，版本号/路径/日志用 `Cascadia Code / ui-monospace / monospace`。不依赖远程字体。
- 可选的标题组合：① 系统无衬线全站（默认）；② 首页展示标题用 `Songti SC`、工作台仍无衬线；③ 如有已授权字体资产，首页展示标题用该字体，正文保持系统字体。可选项只影响品牌表达，不影响操作信息。
- 字阶：展示标题 48–64px；页标题 26–32px；卡标题 20–24px；正文 **15–16px**、行高 1.55–1.7；辅助文字 13–14px；仅日志、路径、时间戳可用 12–13px。按钮正文至少 14px。不要用 10–11px 承载问题、状态、结果或导航。
- 正文每行约 28–40 个汉字；主卡片最大阅读宽度 720px。每屏最好只有一个主卡片完整展开；历史卡片压缩成行或摘要。

### 5.3 后续二次元皮肤（MVP4）

只替换语义 token、标题字体、插画槽与轻动效；页面结构、字段、文案、状态含义、焦点与对比度不变。建议采用“轻小说创作台”而非满屏霓虹：深蓝灰底、局部珊瑚/薄荷强调、克制的角色剪影仅在首页/空状态，确认卡与预览保持清晰。切换即时生效，偏好持久化，切换过程中不丢草稿。上线前两主题均跑相同的可访问性与流程用例。

## 6. 组件与交互状态

| 组件 | 默认与内容 | 状态 | 关键规则 |
| --- | --- | --- | --- |
| 主按钮 | 文字 + 可选尾箭头 | hover / focus / disabled / loading | loading 禁止重提；文字说明正在做什么 |
| 次按钮 | 线框或文字 | hover / focus / disabled | 不能与主动作同等视觉重量 |
| 文本域 | 常驻标签、说明、计数 | focus / error / unsaved | 输入错误在字段旁、保留原文 |
| 问题组 | 问题、影响、建议、选择 | 未答 / 已答 / 过期 | 题间距 ≥24px；过期时保留草稿比较 |
| 决策卡 | 编号、标题、状态、内容、动作 | 等待 / 已确认 / 失效 | 等待态展开；其余折叠为摘要 |
| 阶段条 | 当前阶段与短文案 | 等待 / 进行 / 完成 / 失败 | 不以颜色单独表达，不显示假百分比 |
| 事件行 | 时间、事件、查看详情 | 新 / 已读 / 失败 | 默认只展示与当前任务相关的最近项 |
| 版本切换 | 版本号、时间、成功状态 | 当前 / 历史 / 加载失败 | 明示历史版本，不自动改变业务数据 |
| 预览容器 | 应用、视口切换、重载 | 启动 / 可用 / 失败 / 过期 | 失败显示原因和恢复动作，不画假内容 |
| 抽屉/对话框 | 标题、说明、动作 | 打开 / 关闭 | 打开聚焦标题或首控件；Esc 关闭并还原焦点 |

## 7. 桌面尺寸、键盘与无障碍

- 1280–1440px 桌面为验收区间：导航 + 当前工作 + 条件式证据/预览。空间不足时先压缩或收起导航与辅助区，不压缩当前卡片文字。小于 1280px 不交付手机专用页签或触屏流程。
- 主卡片不锁在固定高度的裁切容器；页面负责自然滚动，日志与代码才用局部滚动。
- 跳过导航链接、语义标题层级、可见 label、自然 Tab 顺序、Esc 关闭抽屉；异步结果用 `aria-live` 的简短状态，避免整段卡片重复播报。
- 正文与背景对比至少 4.5:1，大文字至少 3:1；焦点建议 2–3px 实线且清楚可辨。依据 [WCAG 2.2 对比度](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum) 与 [焦点外观说明](https://www.w3.org/WAI/WCAG22/Understanding/focus-appearance)。状态另配文字；减少动态效果偏好下停用循环动效。
- 网络、模型、构建可能耗时：页面可继续阅读历史；按钮显示提交中；中断时保留未提交输入。不要用会跳动的 skeleton/动画制造“忙碌感”。

## 8. 与当前代码的差距及实施顺序

截至 2026-10-31 的 `web/src/styles.css` 有完整暖色基础，但多处核心文字为 10–12px，桌面顶部 94px，右侧结果区在没有版本时仍占 300–340px，深色导航的视觉重量也较强。这些是当前实现观察，不等于已通过浏览器走查。

1. **P0 可读性与首屏**：将问题、计划、导航、状态和按钮正文提升到上述字阶；顶部收至 64–72px；在 1366×768 验证主卡标题、第一题和主动作可见或清楚可达。
2. **P0 阶段聚焦**：无版本且等待决策时收起右区；仅在有可用版本时显示证据摘要；历史事件默认折叠。保留既定三块信息架构与服务端状态契约。
3. **P1 结果证据**：测试结果将“通过/失败/未执行”分列；日志按需展开；无预览入口时明确未接入。
4. **P1 键盘与恢复**：在桌面目标视口完成澄清和计划确认；面板关闭后焦点返回触发按钮；网络断开/冲突时保留草稿。
5. **MVP2**：预览就绪后调整左右比例，使预览成为主角；此时再加入视口切换与预览错误态。

实现入口：`web/src/styles.css` 的桌面布局与字阶；`web/src/App.tsx` 的阶段条件渲染、历史折叠与焦点恢复。不得只改视觉而绕过后端的确认门禁。旧原型中的手机专用 CSS 与手机插图不作为实施要求。
