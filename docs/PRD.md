# MYATOM 产品需求文档（PRD v0.1）

状态：设计基线，2026-10-30；2026-10-31 用户明确将 MYATOM 建造工作台调整为桌面优先，取消移动端适配与验收，并确认生成交付物的持久化及回滚边界（见 [ADR-004](decisions/ADR-004-generated-deliverable-boundaries.md)）；2026-11-01 确认单次主线交付范围及[单一发送交互](decisions/ADR-010-structured-card-single-send.md)。架构实现见 [系统架构](ARCHITECTURE.md)，变更规则见 [ADR-002](decisions/ADR-002-change-control.md)。平台前置验证的过程记录在本机 `D:\AI\ATOM笔试\docs\ATOMS-SPIKES.md`；它不随代码仓库分发。

## 1. 目标与定位

面向笔试评审展示一个可运行的 Atoms 类网页应用：用户用自然语言提出 Web 应用需求，系统澄清并补全需求、展示可修改的计划，单 Agent 实际生成固定模板中的代码，用户在网页上操作生成结果，并在刷新或重新进入项目后继续。可用性与真实闭环优先于覆盖 Atoms 全量能力。

**成功标准**：评审可从一个公开在线链接进入 Demo，独立完成一次生成、操作生成应用、刷新恢复项目，并看到至少一个延展能力；主流程不能由预置静态截图或假进度替代。公开交付主路径已确定为 GitHub → Azure，见 [ADR-014](decisions/ADR-014-atoms-deployment-and-model-credentials.md)；在线地址及功能须在实际 Azure 测试域通过验收后补入交付记录。Atoms Spike 保留为可选迁移研究，不作为本轮上线前置条件。

## 2. 用户与范围

- 主要用户：输入想法、希望快速看到可操作 Web 原型的非专业或轻技术用户。
- 评审任务：验证真实模型决策、真实代码生成、预览交互、数据持久化与故障反馈。
- 平台借鉴：围绕软件产品生命周期的“提出需求—构建—测试—发布/迭代”，而非复制 Atoms 的多 Agent、全部云服务或完整 UI。

**首版不承诺**：任意技术栈生成、多 Agent 协作、商用支付、完整 A2UI 协议、跨项目自动推理记忆、生产级多租户代码执行。注册/登录是否接入平台身份服务由 Spike 决定；MVP1 至少提供可恢复的访客项目身份和清晰的项目入口。MYATOM 自身的项目与版本不能只靠浏览器本地存储；**生成应用自身的业务数据**按 §5 的限定使用 `localStorage`，两者不得混淆。

**当前工作流范围**：一个 run 接收一条简单需求，沿澄清 → 计划 → 生成 → 检查 → 交付主线完成一版应用。澄清补问、计划原阶段修改、源码校验和构建失败修复是有上限的局部循环；不做复杂需求触发的跨阶段自动回退，也不识别“新建内容 / 修改内容 / sidecar 聊天”等全局意图。只在当前待决卡所属阶段内解释回答、修改、提问和明确批准，受确定性门禁约束。交付后再次迭代由明确的用户操作创建新 run；版本回滚是独立的快照操作，不属于 Agent 阶段回退。细则见 [ADR-006](decisions/ADR-006-single-main-run-scope.md)、[ADR-010](decisions/ADR-010-structured-card-single-send.md) 与 [ADR-013](decisions/ADR-013-source-validation-targeted-repair.md)。

## 3. 关键用户旅程

1. 打开站点，创建项目，输入目标、目标用户和关键功能；获得项目链接/ID。空需求、过长输入和重复提交有明确反馈。
2. Agent 至少发出 1 张、最多 3 张**需求澄清卡**，每张提出 1–3 项影响实现的非重复关键问题。用户逐轮回答、修改本轮需求或接受默认值；每轮确认后判断剩余缺口，足够明确才进入计划。第 3 轮仍不充分则说明原因并结束当前 run。
3. Agent 给出**Build Plan 确认卡**：页面与交互、数据模型、技术模板、验收点、预计代价/限制。用户可在计划阶段提出修改意见；确认生成不可变的 `approved_spec_version`。若计划发现需求范围冲突或关键缺口，说明原因并结束当前 run，不自动退回澄清阶段。
4. Agent 按计划写入项目工作区，安装/构建/测试并报告实际结果；主对话只显示用户能理解的当前阶段、失败原因和下一步。文件变更、构建命令与用量等诊断信息在对应的测试/管理视图按需查看，不把模型调用事件堆进对话。自动修复达到上限后，构建失败先给出问题小结并等待人工决定：继续修复一次、指定源码修复方向或用现有代码重新构建；每次都需用户明确提交，不盲目重试。其他失败按类型结束或要求重新提交需求。见 [ADR-008](decisions/ADR-008-manual-build-recovery.md)。
5. 用户打开预览，点击、输入、提交、刷新生成应用，并在主应用中查看**测试结果卡**。生成应用的业务数据写入其预览 origin 下的 `localStorage`；同一项目须使用稳定且与其他项目隔离的 origin，使同一浏览器刷新或重新打开后数据仍可读，其他项目不能读取。界面明确说明浏览器清理存储、换设备/浏览器或更换 origin 时不保证数据恢复。
6. 用户返回项目列表或用原链接重新进入，恢复会话、计划、事件、生成版本与预览入口；可在已有项目中追加修改需求，形成下一版本。用户可从最多 5 个已保存的可用版本中选择旧版并回滚当前代码指向，不调用模型重新生成。

### 异常旅程

- 断网/刷新：界面根据服务端项目状态与事件游标恢复，不重复启动构建。
- 模型超时/额度不足：呈现可解释状态、剩余额度或停止原因；保留最后一个可用版本。硬预算耗尽时暂停当前 run，展示触发项及四项已用量/上限；项目拥有者明确选择扩额并确认后继续原检查点。新 run 默认 100,000 Token；每次确认可再增加 100,000 Token，也可选择增加模型调用次数、Agent 执行时间或自动修复轮次。没有确认不自动继续。见 [ADR-015](decisions/ADR-015-owner-confirmed-budget-extension.md)。
- 计划生成失败：主对话说明计划未通过的具体受控原因（如缺少刷新读回验收、数据模型缺少本地存储说明或超出存储边界），不误称构建失败，不展示虚假的构建检查。独立异常后台按 Trace ID 展示相同的安全原因；不返回模型原文或堆栈。没有已批准计划与源码候选时，用户可核对原需求后开始新一轮。
- 单 run 默认 15 分钟时长预算只累计 Agent 执行阶段；等待澄清答案、计划确认、额度确认或修改及服务停机不计时。多段执行累计使用同一预算，人工扩额只增加上限、不清零已用量，详见 [ADR-007](decisions/ADR-007-active-execution-budget.md) 与 [ADR-015](decisions/ADR-015-owner-confirmed-budget-extension.md)。
- 源码校验及编译/类型错误：初次生成后默认共享最多 60 轮自动源码修复，用户明确扩额后可提高轮次上限；最近 3 次错误集合相同，或某个错误累计第 5 次出现时提前停止并交人工。校验或构建诊断能定位文件时仅重新生成该文件，其他候选文件不变；无法定位才全量重生，且每次都重新校验完整候选。展示停机原因、最近错误、累计尝试和可用日志入口；用户可定向再修一次，已有构建候选可原样重建，沿用同一 run 的模型、token 与执行时间预算。环境故障只可在人工排查后主动重新构建，不让 Agent 盲改源码。见 [ADR-009](decisions/ADR-009-build-repair-harness.md) 与 [ADR-013](decisions/ADR-013-source-validation-targeted-repair.md)。
- 仅因自动修复轮次上限而暂停时，人工卡允许用户选用“增加 30 轮自动修复并继续”并发送；额度先持久化，再从当前候选检查点继续。连续无进展与同错复现的提前停机规则仍生效，见 [ADR-015](decisions/ADR-015-owner-confirmed-budget-extension.md)。
- 构建检查的每次失败（含自动修复中的中间失败）写入独立异常中心的安全警示，关联 Trace、构建轮次、固定命令、退出码、耗时、错误码/指纹、目标文件和当时用量；通过的检查也保存指标。模型在 CodeLoop 修复时输出结构失败、但可恢复的构建候选与检查点仍在时，项目拥有者可主动打开人工修复卡后明确继续；不自动重试模型。见 [ADR-016](decisions/ADR-016-build-check-observability-and-recovery.md)。
- 运行环境不支持：禁用不安全的交互预览，显示构建产物与环境原因，走本机 Atoms Spike 过程记录的备用路径。

跨项目异常排查由[独立部署的管理员异常后台](EXCEPTION-OBSERVABILITY.md)承担。主工作台仅写入脱敏记录，不增加普通用户导航或跨项目读取入口；部署边界见 [ADR-003](decisions/ADR-003-exception-console.md)。

## 4. 界面与结构化呈现

首页提供三个可编辑的需求示例：[番茄钟待办、点老头游戏、移动点单](../examples/catalog.json)。选择示例仅填入草稿，不自动调用模型；用户仍需提交需求、确认澄清与计划。三个示例分别用于校准浏览器业务持久化与计时、皮肤与高频点击、点单流程及生成应用的手机适配；验收步骤见 [示例 TC](../tests/cases/EXAMPLES.md)，交互见 [示例 UI](EXAMPLE-UI.md)。移动点单在当前固定 Web 模板内交付“小程序风格移动 H5”，订单状态保存在当前浏览器，不承诺原生微信小程序、真实支付或跨用户订单同步。若该交付物包含后端，也须遵守 §5 的单进程/单端口及无服务端业务持久化边界。

主布局：项目侧栏、对话、按阶段出现的右侧成果区。澄清、用户回答、计划、确认、生成进度和结果按时间顺序组成对话；当前待决卡嵌在 Agent 消息里，提交后留下只读摘要。无可用版本时，工作台右侧默认不占空间，计划形成后可手动打开文档；有真实可用版本时再展示预览/代码。旧版已存在而新一轮仍在生成时，用户仍可查看旧版。正常用户不看到原始事件清单、模型调用数、Token 或内部 run ID；失败信息可按需查看用于报障的 trace ID。桌面工作台的两条分隔线可调整宽度；仅将布局偏好保存在当前浏览器的 localStorage，并可恢复默认，不影响项目数据。MYATOM 建造工作台只按桌面浏览器设计和验收，不交付手机专用布局或手机视口用例；生成出来的应用是否支持手机，由该应用的需求与模板能力决定。过程信息使用受版本控制的轻量 JSON 卡片（`type`、`schema_version`、`card_id`、`run_id`、`status`、`payload`、`actions`）；前端只渲染已知类型，未知类型降级为安全文本。用户操作提交到后端状态机，后端校验当前阶段与版本，前端拦截只是体验层。

当前待确认的澄清、计划或构建失败卡与唯一消息输入区处于同一条 Agent 对话，卡片下方只有一个对话提交按钮“发送”；不另设分离的固定输入区，也不放确认/修复/原样重建提交按钮。卡片可提供结构化答案、选择和按需展开的详情；计划在主对话展示拟做任务清单，其他详细内容在详情及项目文档中可读。用户发送的原文与答案快照进入时间线，解释结果可刷新恢复。澄清答案齐全时允许无文字发送；补充或修改需求优先于旧卡确认。计划阶段的消息可提问、修改或明确批准；“可以”“确认”“继续”不得批准，修改加批准只修改计划，新卡仍需明确批准。构建失败时通过文字明确要求单次修复、指定源码修复方向或原样重建，受错误类别及当前卡动作白名单约束。主动点击“修改原需求”才在同一输入区进入全文编辑，并可取消。输入区只显示 `n/上限` 字数；Enter 发送，Shift+Enter 换行，输入法组合输入期间不发送。生成中允许先写草稿，待本轮结束后由用户显式创建新 run；未发送草稿仅保存在当前浏览器会话，服务端仍是已提交项目数据的权威来源。详见 [单一发送交互决策](decisions/ADR-010-structured-card-single-send.md)及[决策对话布局修订](decisions/ADR-011-decision-turn-composer.md)。

额度确认卡嵌在当前 Agent 回复中，列出已耗尽原因、四项已用量与当前/确认后上限。用户勾选额度后只有一个“确认扩额并继续”提交动作；当前耗尽项不可漏选。卡片版本与幂等键由服务端校验，旧卡不能再次扩额。旧终态额度任务需先由拥有者主动打开扩额选项。

长任务进展按 [ADR-012](decisions/ADR-012-user-facing-run-progress.md) 实施：澄清每轮交代已确认内容与下一步；计划形成后把 `tasks` 列为**拟做**清单；批准后另以源码写入、构建命令、静态资源检查和版本保存的真实记录更新执行清单。累计执行时间只计 Agent 工作，不计等待用户；连接中断冻结最后同步值。结束或暂停后过程默认折叠，结果/人工决定在前；浏览器交互若未实测必须标“未检查”。

| 卡片 | 最小内容 | 用户动作 | 时点 |
| --- | --- | --- | --- |
| 需求澄清 | 已知/假设/问题、默认值、风险 | 回答、编辑、确认 | MVP1 |
| Build Plan | 页面、功能、数据、技术选型、验收点 | 本阶段修改、确认 | MVP1 |
| 构建进度 | 阶段、已完成步骤、文件摘要、耗时/预算 | 取消、查看详情、重试 | MVP1 |
| 测试结果 | 构建/单测/浏览器检查、失败定位、版本；失败时附人工可读小结 | 查看、继续修复一次、指定修复方向、用现有代码重新构建、必要时新建 run | MVP1–2 |
| 架构图与图表 | 模块关系图、阶段/用量图；来源与时间戳 | 展开、查看数据 | MVP3 |

图和图表是决策说明及运行结果的投影，不能代替原始状态、测试日志或实际预览。图结构从受限 schema 渲染；不得直接执行模型返回的 HTML/脚本。视觉主题使用设计 token（颜色、字体、圆角、插画位、动效强度），至少有默认主题与二次元主题；主题只改变表现层，不改变业务状态和可访问性。二次元主题用于年轻用户表达，避免将审美假设当作已证实增长结论。

## 5. 持久化与版本

**MYATOM 平台数据**：服务端保存项目、会话、用户输入、确认结果、事件、生成交付物快照、测试摘要和预览状态。浏览器对这些平台数据仅保存恢复用的最小项目标识/会话凭证，不能作为唯一数据源；布局宽度是非业务界面偏好，可仅保存在本机 `localStorage`。

**部署数据边界**：本地与 Azure 是两套独立数据环境。Azure 首次启用从新项目开始，不搬迁本地历史项目、会话、checkpoint、可用版本或交付文件；本地旧数据仍可在本地环境访问。两套环境的新数据分别按各自的持久化方案验收。

**生成交付物范围**：固定 React + TypeScript + Vite Web 模板。生成应用的业务数据只允许写入其自身预览 origin 的 `localStorage`；同一项目跨版本保持稳定 origin，不同项目必须有真正的 origin 隔离，单靠存储键名前缀不构成安全隔离。不生成 SQL 数据库、缓存、远程业务存储或 MYATOM 服务端业务数据 CRUD。若确需生成应用后端，最多启动一个后端进程、监听一个端口，且不负责业务持久化；无后端也是合规方案。这个端口限制只约束**生成交付物自己的后端**，不计入 MYATOM 主 API、预览网关或独立异常后台的端口。计划卡和生成校验须提前说明并拦截超出边界的需求。

**交付物版本与回滚**：每个向用户呈现为“可用版本”的产物，必须是完整持久化、构建及预览可用性检查通过的不可变快照，包含源码、静态资源、依赖锁/模板标识、构建产物、manifest 和测试结果引用。每项目最多保留 5 个可查看、可预览、可回滚的可用快照；新版本成功入库并切为当前版本后，淘汰最早且非当前的快照。失败产物可留诊断记录，但不占可用版本名额，也不能替换或删除当前可用版本。项目持久化 `active_version_id`；回滚只把它切换到现存旧快照，不重新生成、不新增快照，刷新/重新进入后仍指向该版本。重新迭代成功则产生新快照。

**下一版继承**：在已有可用版本的项目提交新要求时，新 run 固定当时的 `active_version_id` 作为基线；本轮输入是变更要求，不要求用户重写全部历史需求。计划卡列出新增、调整、删除以及折叠的沿用功能，完整有效规格保存到新版本 manifest。删除或替换旧功能必须在计划中明确列出并由用户确认；其他已确认功能、数据模型和验收点默认保留。代码从基线完整源码快照开始，优先只更新计划指定文件；检查不通过时保留旧版和本轮诊断。构建与静态预览探针只证明编译和资源可用，旧功能的真实浏览器行为仍以回归用例为准。详细契约见 [ADR-019](decisions/ADR-019-version-inheritance.md)。

版本列表应标出“当前版本”和每个快照的生成时间/测试结果；**临时查看旧版**只改变当前页面的预览选择，用户明确执行“设为当前版本”才提交回滚。达到 5 版后，新成功版本将淘汰哪一版须在再次生成前告知；回滚成功后列表与预览都显示新的当前指向。若当前没有可用版本或目标已被淘汰，回滚入口禁用并说明原因。

**业务数据不随代码回滚**：`localStorage` 不纳入快照、不随版本选择或回滚改写。这里的“可用回滚”只保证旧代码/构建产物可恢复并可打开，不保证旧代码与现存浏览器数据结构兼容；若发生不兼容，须明确提示用户，不把数据迁移或数据库/缓存回滚纳入本轮范围。浏览器清理存储、跨设备/浏览器和预览 origin 变化均不保证业务数据恢复。具体契约和现状差距见 [ADR-004](decisions/ADR-004-generated-deliverable-boundaries.md) 与 [架构](ARCHITECTURE.md)。

## 6. 分期与验收

| 阶段 | 范围与交付 | 退出条件 |
| --- | --- | --- |
| MVP1 基础闭环 | 创建/恢复项目、一条简单需求的 1–3 轮澄清、计划确认、单 Agent 生成代码、保存版本、构建/测试结果卡 | 真实模型与文件写入；刷新后项目、确认和产物可恢复；可修复构建错误有限自动重试，耗尽后等待人工明确动作，其他失败按类型结束 |
| MVP2 实时查看 | 事件流、连接恢复、隔离预览、预览内真实交互及数据持久化；可用版本回滚 | 在浏览器完成生成应用的一条业务流程；同浏览器、同项目稳定 origin 刷新后 `localStorage` 数据仍在且跨项目不可读；断线后进度不丢；最多 5 个完整可用快照并可持久回滚 |
| 校准 | 用评审任务走通完整链路，按实际耗时、成本、错误修复优先级 | 至少一条端到端演示录屏/记录；阻断缺陷清零 |
| MVP3 结构化决策 | 图表、架构图、测试/风险说明卡；卡片版本降级 | 卡片与服务端状态一致；图表可追溯数据来源 |
| MVP4 双主题 | 默认与二次元主题、可切换并持久化偏好 | 两主题在桌面浏览器的空/加载/错误态可用，核心流程一致 |
| MVP5 记忆候选 | 经用户确认后，最小的事实偏好、跨项目资料索引、历史技能/结论引用 | 可查看来源、更正/删除；错误记忆不自动写入计划。若资源不足，明确不交付 |

笔试最低交付门槛是 MVP1+MVP2 与至少一个可用延展点（优先 MVP3 的结构化卡片或 MVP4 的双主题），以及可测试的在线访问链接。GitHub → Azure 路线须提供持久状态、隔离 Runner 与稳定预览 origin；不能因为主 API 容器启动成功就删去真实交互或持久化要求。部署闸门见 [Azure 部署 TC](../tests/cases/DEPLOYMENT-AZURE.md)。

## 7. 测试与 TC 维护

- **设计 TC**：澄清/确认卡信息层级、状态与错误文案、桌面基准视口、键盘可操作、主题一致性。用于 PRD/视觉变更和 MVP3/4 回归。
- **前端 TC**：阶段门禁、重复确认、断线重连、事件去重、未知卡片降级、项目恢复、预览跨域隔离。用于 UI、协议和连接层变更。
- **后端 TC**：状态转移、确认版本、工具权限、超时/429/5xx 退避、幂等写入、预算截断、checkpoint 恢复、构建修复上限、项目隔离。用于每个 Node/Harness/存储变更。
- **端到端 TC**：全新项目 → 生成 → 构建 → 预览提交数据 → 同浏览器、同项目稳定 origin 刷新/重进 → `localStorage` 数据恢复；验证另一项目的预览代码不能读取该存储。另测失败修复、取消、断线、旧版本。版本验收包括连续生成第 6 个成功版本后只保留 5 个、失败不淘汰当前版本、回滚后刷新仍指向旧快照，以及回滚不改写浏览器业务数据。用于每个 MVP 出口和上线前。

实施变更的 Agent 同时更新 TC、预期、执行记录与未验证边界。可使用 `tests/cases/` 和 `tests/evidence/`（后续建代码时创建）；测试不得只断言“页面能渲染”。

首批必须落地的用例：`TC-E2E-01` 新建项目至预览提交一条待办并刷新读回；`TC-BE-01` 计划未确认时写文件请求被拒；`TC-BE-02` 同一确认/工具操作重放不产生重复版本；`TC-FE-01` SSE 断开后回放缺失事件且卡片状态一致；`TC-SEC-01` 预览代码无法读取主应用密钥与其他项目数据。记录步骤、输入、预期、实际、环境、版本和证据链接；上线前在公开 URL 复跑 `TC-E2E-01`。
