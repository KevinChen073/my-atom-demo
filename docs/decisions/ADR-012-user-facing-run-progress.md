# ADR-012：长任务的用户可见进展

- 状态：Accepted（用户于 2026-11-01 确认节点进展方案）
- 关联：[PRD](../PRD.md)、[架构](../ARCHITECTURE.md)、[MVP1 UI](../MVP1-UI.md)、[设计交互](../../design/INTERACTIONS.md)、[TC](../../tests/cases/RUN-PROGRESS.md)、[变更守则](ADR-002-change-control.md)

## 决定

1. 对话只保留一条随当前阶段更新的进展消息。澄清每轮说明已确认的信息及下一步；计划形成时以未完成清单列出拟做任务，确认前不得出现“已完成”勾选。
2. 生成时另列实际执行清单：源码写入、构建命令、静态预览资源检查、可用版本保存。只有对应持久事件或版本入库事实可标通过；失败、进行中和未执行分别标明。静态资源可读不等于浏览器交互通过。
3. 显示累计 Agent 执行时间，以服务端持久计时为准；等待用户回答/批准/修复、排队和服务停机不计。连接中断时冻结最后同步值并说明连接状态，恢复后对账。
4. 等待用户决定时当前决策卡仍是主焦点，进展仅作简短上下文。完成、失败、取消或暂停待人工修复后，结果或处理动作在前，过程默认折叠；展开才看清单。普通对话不展示原始事件、模型调用、Token 或内部 run ID。
5. 当前澄清实现是有界结构化模型调用加确定性完整性门禁，不把它描述为可任意调用工具的 ReAct。进展只投影真实状态，不增加新的执行分支。

## 数据依据与限制

`phase` 记录当前节点；`clarity_result` 记录本轮已确认问答与剩余缺口；计划清单来自已保存 `plan.tasks`；`files_written`、`build_result.steps`、`preview_check`、`completed/version_saved` 驱动执行清单。`active_elapsed_seconds` 和 `execution_running` 由服务端返回。历史 run 若缺事件，界面保持未证实状态，不能按当前 phase 反推过去每一步通过。

历史计划若缺 `tasks`，界面降级展示 `features` 作为拟做清单；它仍不代表已经实现。

本决定细化 [ADR-005](ADR-005-conversation-first-results.md) 的“用户可理解进展”，并取代旧 [MVP1 UI §4.3](../MVP1-UI.md#43-构建进度卡) 对每个阶段都常驻展示时间戳与耗时的表述；逐命令证据仍在测试视图查询。
