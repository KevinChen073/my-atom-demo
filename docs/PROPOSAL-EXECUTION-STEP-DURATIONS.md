# MYATOM 执行步骤耗时展示技术建议

状态：**待评审建议稿**，2026-11-01。本文只提出改造方案，不修改现行 [PRD](PRD.md)、[MVP1 UI](MVP1-UI.md) 或已接受的 [ADR-012](decisions/ADR-012-user-facing-run-progress.md)，也不表示功能已实现。正式实施前按 [ADR-002](decisions/ADR-002-change-control.md) 确认展示规则，再同步设计与验收文档。

## 1. 目标与展示范围

在主对话现有的“实际执行与检查”清单内，为**生成/修复源码**和**构建检查**增加可核对的步骤耗时，保留卡片右上角的整轮累计执行时间。例：

```text
生成源码       已完成 · 耗时 1 分 23 秒
构建检查       进行中 · 已耗时 12 秒  （每秒更新）
静态预览资源检查  待开始
保存可用版本      待开始
```

修复轮次应写成“修复源码（第 1 轮）”；构建失败后再次检查应显示对应的第几次尝试。主清单只显示**当前或最近一次尝试**，较早尝试留在可展开的检查记录。不能把多轮修复的总时间标成最近一次的耗时。

“已完成”只在候选源码确已写入或构建结果确已持久化且通过时出现；失败显示“未通过 · 已耗时 …”，取消显示“已取消 · 已执行 …”。正在修复源码时，构建检查保持“待开始”，直到服务端真正进入 `BuildTest`。耗时不是完成时间预测，不增加百分比或假进度。

## 2. 当前实现与差距

| 当前依据 | 已有能力 | 缺口 |
| --- | --- | --- |
| [工作流](../backend/workflow.py)的 `phase` 事件 | `CodeLoop`、`ValidateSource`、`BuildTest` 等节点有持久事件；[事件表](../backend/store.py)保存 `at` 与 `seq` | 事件时间是墙上时钟，不等于实际执行秒数；同一节点可因修复或恢复而重复进入 |
| `files_written`、`build_result` | 可证明源码已写入、构建已结束；`build_result.steps` 有逐命令 `seconds` | 未提供每次源码生成/构建阶段的权威起止累计值；逐命令秒数也不覆盖完整步骤 |
| `active_elapsed_seconds`、`execution_running` | [服务端](../backend/store.py)提供整轮 Agent 累计执行时长，并以约 5 秒心跳落盘 | 没有按步骤、按尝试分解；停机时最后一个未落盘的短区间可能丢失 |
| [RunProgress.tsx](../web/src/RunProgress.tsx) | 从事件投影通过、失败、进行中，并逐秒刷新整轮计时 | 组件的事件类型尚未使用 `at`，也没有步骤耗时字段或多次尝试规则 |

**仅改前端的轻量方案**：用最近一次 `phase: CodeLoop` 到 `files_written`、`phase: BuildTest` 到 `build_result` 的事件 `at` 相减；构建进行中用浏览器当前时间减 `BuildTest.at`。它可用于即时视觉试验，但会把服务停机算进步骤耗时，并受客户端时钟偏差、重试和阶段事件重复影响；不应作为正式“耗时”记录。

## 3. 推荐数据契约：服务端计时，前端插值

### 3.1 步骤尝试记录

在 MYATOM 的运行存储中增加 `run_step_attempts`，每条记录代表一个 run 中某步骤的一次尝试。最小字段：

| 字段 | 含义 |
| --- | --- |
| `run_id`, `step`, `attempt_key` | 唯一键；首批 `step` 只取 `source`、`build`。`attempt_key` 在执行副作用前确定，重启重放不得新建同一次尝试 |
| `ordinal`, `fix_round` | 用户可读的尝试序号和修复轮次；不靠前端数事件猜测 |
| `state` | `active`、`passed`、`failed`、`cancelled`；恢复中由 `execution_running=false` 派生，避免把停机记为执行 |
| `active_started_seconds` | 步骤开始时服务端整轮累计执行秒数，精度保留小数 |
| `active_finished_seconds`, `duration_seconds` | 完结时的累计值与差值；活动步骤的 `duration_seconds` 暂为空 |
| `started_at`, `finished_at` | 服务端 UTC 时间，仅用于显示/审计，不用墙上时钟相减计算执行耗时 |

数据库对 `(run_id, step, attempt_key)` 加唯一约束。开始和结束操作应与 run 阶段更新、事件追加在同一事务中，避免 UI 看到“构建进行中”却没有计时基线。通过服务端现有的累计执行计时方法读取基线；写入时同步结算当前运行区间，避免与心跳并发导致开始值、结束值错位。结束秒数按 `max(0, active_finished_seconds - active_started_seconds)` 计算。

`GET /api/projects/{id}` 的当前 run 增加 `progress_steps` 投影，包含各步骤最近一次尝试的上述展示字段；新增只读 `GET /api/runs/{id}/progress-steps` 按 `ordinal` 返回全部尝试，供测试/详情视图展开。两个接口沿用现有 run 的访客权限校验。`GET /api/runs/{id}/events` 和 SSE 增加同一尝试的开始/结束通知（含 `attempt_key`、`step`、`state`、`seq`），供页面及时刷新。数据库记录是权威，通知只提示重新取快照；刷新页面无需依赖先前浏览器内存。旧事件的类型和顺序保持兼容。

### 3.2 步骤边界

| 步骤 | 开始 | 结束与状态证据 |
| --- | --- | --- |
| `source` | 进入本次 `CodeLoop`、发起源码生成之前 | `ValidateSource` 通过且 `files_written` 已持久化后为 `passed`；`source_validation_failed` 结束本次尝试为 `failed`，若自动重试则开启新的尝试 |
| `build` | 进入本次 `BuildTest`、调用 Runner 前 | Runner 返回并持久化 `build_result` 后，依 `ok` 为 `passed` 或 `failed`；诊断/后续修复不计入该次构建 |

源码步骤包括模型生成、源码校验与候选文件写入；构建步骤包括 Runner 准备、依赖安装和构建命令。若异常、预算耗尽或用户取消打断步骤，需在 run 转为终态/等待人工时关闭活动尝试，不显示“已完成”。旧的 `files_written`、`build_result` 仍决定是否真实通过，计时记录不能单独作为成功证据。

一次构建失败后的自动源码修复，应创建新的 `source` 尝试；再次构建创建新的 `build` 尝试。仅“用现有代码重新构建”时保留上一次源码通过记录，只新建构建尝试。重启恢复同一未完成节点时复用 `attempt_key` 和原始累计基线；服务停机期间 `active_elapsed_seconds` 不增长，因此不算入步骤耗时。若恢复后实际重新执行节点，应在状态和记录中区分重放与新尝试，不能双计时。

这套耗时精度继承现有整轮计时的约 5 秒心跳：异常断电可能丢失最后一次心跳之后的执行片段，界面不得用停机后的墙上时间补齐。正常完成的步骤在结束事务中结算，可得到服务端记录的完整耗时。

## 4. 前端投影与计时规则

`RunProgress` 从 `progress_steps` 读取状态和基线，而非用事件 `at` 直接相减。活动步骤的显示值为 `run.active_elapsed_seconds - active_started_seconds`；连接正常且 `execution_running=true` 时，在两次服务端快照之间沿用现有整轮计时逻辑每秒插值。收到新快照后以服务端值对账。连接断开、执行停止或服务重启恢复中时冻结最后值，并保留现有连接状态提示；不能继续按浏览器墙上时间增长。

展示以整秒向下取整：小于 60 秒为“12 秒”，否则为“1 分 23 秒”；缺少合法基线或历史 run 无步骤记录时显示“耗时未记录”，不从当前 `phase`、成功文件数或客户端事件时间补造数值。已结束步骤使用 `duration_seconds` 固定值，不受刷新、切项目和时区变化影响。步骤状态同时用文字与图标表达，避免只靠颜色。

主对话保留现有单条进展消息、总执行时间和默认折叠规则。当前阶段相关的最多两个步骤耗时直接出现在清单行；逐次尝试、逐命令时间与诊断仍在测试/详情视图按需查看，避免进展卡变成日志墙。

## 5. 实施顺序与验收

1. **确认展示规则**：本建议会修订 [ADR-012 §决定 3、数据依据与限制](decisions/ADR-012-user-facing-run-progress.md) 及 [MVP1 UI §4.3](MVP1-UI.md)，它们当前规定主对话只常驻累计执行时间、逐节点耗时留在事件/测试视图。确认后写新 ADR 或修订记录，再同步 PRD、设计交互和 TC；建议保留总时长，仅把源码/构建两项耗时提升到主清单。
2. **后端**：加入尝试记录、原子起止操作、当前 run 投影及事件通知；覆盖成功、源码校验失败、构建失败、自动修复、人工原样重建、取消、预算耗尽与重启恢复。既有 run 保持可读，步骤耗时降级为“未记录”。
3. **前端**：扩展 run/步骤类型与 `RunProgress` 渲染，复用已有 1 秒插值、断线冻结和刷新对账；只在服务端证明步骤完成后显示“已完成”。
4. **验证**：用假模型和隔离数据库检查步骤时间不超过整轮累计时间、不同尝试不混算；以可控时钟验证等待人工、停机和断线不增长；浏览器在生成 → 构建、失败 → 修复 → 再构建、刷新/切项目/重连时观察文案与秒数；在 1280×720、1366×768、1440×900 检查清单可读性。

验收时记录 **Pass / Fail / 未执行** 与对应的服务端事件和页面证据。特别检查截图所示“正在修复源码”状态：源码为进行中，构建为待开始；收到新一轮 `files_written` 与 `BuildTest` 后才切为“源码已完成、构建进行中”。

## 6. 推荐与待决点

推荐采用第 3 节的**服务端权威计时 + 前端逐秒插值**。纯前端事件时间差方案可用于原型，但无法满足现行 [ADR-012](decisions/ADR-012-user-facing-run-progress.md) 对停机、等待时间和断线冻结的准确性要求。

待确认的产品规则只有两项：①主对话是否显示源码与构建各自耗时（相对现行 ADR-012 的变更）；②主清单显示最近一次尝试，还是各次尝试累计值。本文推荐“最近一次”，较早尝试留在详情。确认前不把建议稿标为已接受，也不改动现有执行状态机。
