# 示例应用校准验收用例

状态：2026-10-31 草案。范围是首页三个示例需求及其生成产物；依据 [PRD](../../docs/PRD.md)、[架构](../../docs/ARCHITECTURE.md)、[MVP2 用例](MVP2.md)。生成端使用固定 React + TypeScript + Vite Web 模板。第三例明确为“小程序风格的移动 H5”，**不是原生微信小程序**。此处验收的是生成游戏的三套视觉皮肤；MYATOM 工作台双主题属于 MVP4，不与之混同。

**版本标记**：下文服务端 CRUD、禁止 `localStorage`、跨访客订单隔离等条款对应旧版实现，已不适用于 [ADR-004](../../docs/decisions/ADR-004-generated-deliverable-boundaries.md) 的生成交付物目标；不得据此宣称新边界通过。实施迁移时须将示例用例改为同浏览器/同 origin 的本地数据读回与 5 版回滚验收，保留旧记录作为历史证据。

## 执行约定

- 用全新访客身份、新建项目逐例验收；记录示例标题、实际填入的完整需求、澄清卡、批准计划、run/version、模型调用与修复轮次、构建日志、浏览器结果。不要直接批准与示例不符的计划。
- 每例先做无付费的固定源码/假模型回归，再由已授权的真实模型 smoke 验证生成能力。假模型通过只能证明工作台链路和模板能力，不能证明真实模型会稳定生成该应用。
- 只有 `completed`、构建日志通过、版本已保存、独立预览确实可操作、业务数据刷新仍在，才能记为完整通过。失败 run、最后源码的单独重建、静态页面截图分别单列。
- 生成应用只写 `src/App.tsx`、`src/App.css`；若需要业务数据，使用模板 `./appData`，不得将 `localStorage`、外部图/脚本、任意 `fetch` 当成可用方案。测试样例数据使用虚构名称，不使用个人信息。

| 编号 | 操作 | 预期与失败判定 |
| --- | --- | --- |
| EX-CAT-01 展示 | 打开首页，观察示例入口与说明。 | 可辨识番茄钟 Todo、带皮肤的点老头游戏、移动点单三项；移动点单清楚标注“小程序风格的移动 H5 / 当前交付是网页”，不能暗示已交付原生小程序。入口有可访问名称，键盘可聚焦。缺项、重复项或语义不清为失败。 |
| EX-CAT-02 选中填入 | 依次点选三个示例，观察需求输入框；改写输入框后再选另一个示例。 | 每次填入对应完整需求，输入框可继续编辑；点击示例本身不创建项目、run、批准计划或调用模型。切换示例不能拼接旧文本；长度符合输入限制。 |
| EX-CAT-03 既有项目保护 | 在已有项目的“新一轮需求”输入中手写草稿，再返回首页/切换导航，观察示例选择与原项目。 | 不覆盖既有项目已批准的计划、运行或版本；不会把首页示例误提交到旧项目。若产品设计允许在项目中使用示例，应先清楚显示目标项目与新 run。 |
| EX-CAT-04 失败与重复点击 | 连续双击同一示例、刷新页面、模拟获取 catalog 失败（若 catalog 经 API 提供）。 | 内容稳定且不重复；示例选择不触发隐式付费调用；服务失败时可手输需求。 |

## 生成应用可观察验收

| 编号 | 步骤 | 通过标准 |
| --- | --- | --- |
| EX-POM-01 计划门禁 | 选择番茄钟 Todo，提交需求，阅读澄清卡/Build Plan。 | 计划明确任务管理、番茄计时的开始/暂停/重置、会保存的数据与验收点；确认前没有生成工作区/版本。计划漏掉计时或任务持久化时退回修改，不能强行记通过。 |
| EX-POM-02 任务数据 | 预览内新增两个任务，完成其中一个，刷新应用与工作台，再重新进入项目；删除一个任务并再刷新。 | 任务文本、完成状态、删除结果均与服务端一致；跨项目看不到这些任务；没有假成功提示。 |
| EX-POM-03 计时 | 选择任务与 10 秒演示时长，启动计时，暂停等待数秒，再继续至结束；另测重置与切换标签页。 | 倒计时按真实时间差下降；暂停期间不继续减少；继续后到零，当前任务番茄数**恰加一**且刷新后保留；重置回 10 秒且不计数。无需等待正式 25 分钟；刷新后计时是否恢复以批准计划为准，不得误称任务数据持久化等同计时状态持久化。 |
| EX-GAME-01 计划与皮肤 | 选择点老头游戏，确认计划包含目标、分数、10/30 秒回合、重开规则、至少三套可切换皮肤；进入预览。 | 页面确有可见目标和皮肤切换控件；三套皮肤有明显颜色/图形变化，且同一点击规则与可访问名称保持。皮肤切换不能改变当前分数或误触发目标点击。 |
| EX-GAME-02 点击规则 | 选 10 秒演示回合，开始后只点击目标三次，再点击空白处，切换皮肤，再点击目标一次；等回合结束后再点击，最后重开。 | 每次合法点击加一分，空白点击不加分；切换皮肤后分数连续；结束态不继续加分；重开重置本局状态。正式和演示回合都计入最高分；最高分和选中皮肤刷新后须从服务端读回；仅有本局临时分数不能冒充持久化能力。 |
| EX-GAME-03 资源与移动视口 | 检查默认/第二皮肤，模拟窄屏触摸操作并查看源码/构建日志。 | 目标仍可点击、文本可读；皮肤使用允许的内置 CSS/元素或经审核的静态资产，不依赖第三方图片地址、任意脚本或浏览器本地存储。 |
| EX-GAME-04 快速连点结算 | 新开 10 秒演示回合，在约 2 秒内连续点击目标至少 10 次；记录页面显示的本轮最终得分，待倒计时结束后记录最高分，再刷新页面。可重复一轮以覆盖旧最高分。 | 回合结束按**最终本轮分数**结算，最高分至少等于本轮得分，刷新后仍成立；不得因并发保存或丢弃在途写入漏掉最后一分。若显示“新纪录”但持久化最高分较低，判失败并记录两个具体分数。 |
| EX-ORDER-01 范围门禁 | 选择移动点单示例，检查示例文案、澄清/计划和源码模板。 | 计划与源码均明确 React Web 移动 H5；若模型转向微信原生小程序，退回修改，不以 Web 构建成功冒充原生小程序通过。 |
| EX-ORDER-02 下单主流程 | 在 375 和 390 像素视口打开生成 H5，从 4–6 个固定菜品中选菜，加入购物车，增减数量，核对逐项小计与总价，输入取餐姓名，提交一笔测试订单。 | 价格与数量按固定菜单计算可核对；空购物车和姓名为空时阻止提交；提交后得到订单编号、明细和状态；不接真实支付。点击控件和键盘均可操作，桌面居中展示。 |
| EX-ORDER-03 持久化与隔离 | 提交后刷新应用、重进项目，检查订单；另一个项目尝试访问原项目订单。 | 订单由受控服务端实体保存，刷新后可读，跨项目拒绝；重复提交同一幂等键不创建两笔。购物车刷新是否保持按批准计划判定，不能只用内存购物车代替已提交订单持久化。 |

## 公共失败恢复与记录

| 编号 | 步骤 | 预期 |
| --- | --- | --- |
| EX-COM-01 生成失败 | 注入 TypeScript 构建错误或预览服务不可用；查看测试结果卡和旧版本。 | 失败原因/构建日志可见，不保存假通过版本；旧成功版本仍能查看。修复轮次受预算限制。 |
| EX-COM-02 受控数据失败 | 使预览数据 API 返回 4xx/5xx 或会话过期，再尝试提交。 | UI 呈现失败，可重新授权或重试；不显示虚假保存；网络重试不重复业务记录。 |
| EX-COM-03 真实模型 smoke | 每例只在明确授权的预算内跑一次完整链路，必要时记录修复轮次；浏览器按上述场景验收。 | 逐例记 run 最终状态、token/调用数、构建结果、是否真正浏览器操作、刷新读回和证据；不得将假模型或静态构建结果写成真实模型端到端通过。 |
