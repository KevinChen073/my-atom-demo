# MVP1 验收用例（v0.1）

依据：[PRD](../../docs/PRD.md)、[架构](../../docs/ARCHITECTURE.md)、[单次主线范围](../../docs/decisions/ADR-006-single-main-run-scope.md)、[仓库约束](../../AGENTS.md)。本文件是目标执行清单；新增的澄清轮次/主线范围用例尚未执行，不能当作现有代码能力。每次运行在 `tests/evidence/` 或测试报告中记录环境、提交/构建版本、模型与模板版本、执行时间、实际结果、失败截图/日志引用、`project_id`、`run_id`、`version_id` 与 `trace_id`。证据必须脱敏。自动化用例可使用固定响应的假模型注入故障；**真实生成验收必须调用实际配置的模型并检验写入的文件与构建结果**。

## 适用范围与前置条件

- MVP1 范围：创建/恢复访客项目、需求澄清与计划确认门禁、单 Agent 生成 React + TypeScript + Vite 源码、构建/测试报告、不可变版本与失败恢复。交互预览、预览内业务数据持久化、SSE 实时恢复是 MVP2 门槛，不可把 MVP1 的静态构建产物冒充完整 Demo。
- 测试前准备隔离的数据目录和数据库；使用不含真实用户数据的测试需求，配置 `MODEL_API_KEY` 与可用的模型服务。记录已选 Runner 的隔离方式；同宿主 fallback 只在本地可信测试环境执行，不能面向公网运行不可信代码。
- 创建两个独立访客身份 A/B；准备一条可实现的需求，例如“做一个待办事项单页，能新增、标记完成、筛选待办”。另准备空输入、超长输入、需要澄清的含糊需求。涉及模型输出的断言检验结构、可执行性和批准的需求边界，不断言固定措辞。
- API 名称采用架构文档的契约；若实现路由调整，测试按同等语义映射并在证据中列出。以服务端状态/数据库/磁盘产物为真值，不以页面动画或模型口头声称为真值。

## P0：主流程与门禁

| ID | 操作 | 预期与判定 |
| --- | --- | --- |
| TC-M1-E2E-01 真实生成 | A 创建项目，提交上述待办需求；逐项回答澄清卡，确认计划卡；等待生成完成。检查活动流、测试结果卡、源码文件、manifest/hash 和构建命令结果。 | 有真实模型调用记录与用量/保守估算；生成的 `package.json`、React/TS 文件实际存在且内容对应批准计划；构建实际执行并成功，结果卡与真实日志一致；形成一个不可变版本。仅预置页面、假进度、模型只返回文字均失败。 |
| TC-M1-FE-01 需求输入 | 分别提交空白、超长、重复点击提交，再提交有效需求。 | 前两种被明确拒绝或要求缩短；重复点击不产生多个 run；有效需求可进入澄清。输入和错误文案不会被当成 HTML 执行。 |
| TC-M1-BE-01 澄清门禁 | 用含糊需求发起 run，查看每张 1–3 项关键问题及假设；不回答时尝试调用计划确认/生成接口；回答后修改其中一个答案并确认。 | 未满足澄清条件时不能越过确认进入文件写入；答案进入新版 spec/计划，旧卡动作失效；服务端对阶段校验，而非只禁用前端按钮。 |
| TC-M1-BE-02 计划门禁 | 取得计划卡后检查页面、功能、数据、模板、验收点与限制；在确认前直接调用生成/工具相关接口；提出本阶段修改意见，随后确认新版计划。 | 计划未确认时工作区无生成文件、无构建/发布；修改产生新版计划卡，确认后有不可变 `approved_spec_version`；生成产物与批准版一致。 |
| TC-M1-BE-03 过期决策 | 保存旧 `card_id/spec_version`，修改澄清或计划后重放旧确认。 | 返回冲突/当前卡片，状态与批准版本不倒退，任何文件和版本计数不增加。 |
| TC-M1-BE-12 本阶段修改与旧卡 | 在澄清阶段修改本轮需求并确认；在计划阶段提交修改意见。分别重放旧澄清/旧计划卡；最后检查工作区。 | 本阶段修改产生新版卡和更高 `spec_version`；旧卡返回 409；计划卡没有返回澄清动作，计划批准前没有生成工作区或版本。 |
| TC-M1-BE-16 澄清 1–3 轮 | 分别构造首轮回答即完整、第二/第三轮才完整、第三轮仍缺关键约束的需求；每轮尝试让模型输出 0 题、4 题或重复题，并在等待期间刷新/重进。 | 每个 run 至少 1 张、最多 3 张用户可见卡，每卡 1–3 个非重复问题；已确认事实不重问；完整才进计划，第三轮仍不充分进入终态并说明原因；刷新或重复确认不增加卡数。 |
| TC-M1-BE-17 单次主线边界 | 在计划阶段提交无法满足固定模板的范围要求；在结果失败后输入一条新需求；尝试向同一输入区输入“另开 sidecar 聊天”之类文字。 | 范围冲突明确结束旧 run，不自动跳回澄清/计划；新需求仅通过显式新建动作创建新 run；系统不臆测新建/修改/sidecar 意图，也不静默创建旁路会话。 |
| TC-M1-E2E-02 恢复 | 在等待澄清、等待计划、生成中、生成完成四种状态分别刷新页面/重新打开原项目链接；重启 API 后再打开完成项目。 | 项目、输入、卡片、确认、事件、运行状态、版本和产物都从服务端恢复；等待态可继续操作；生成中不因刷新启动第二个 run；完成版本可再次读取。浏览器缓存清空后，持有效访客凭证仍可恢复。 |
| TC-M1-FE-03 项目直达链接 | 构建主前端后在地址栏直接打开 `/projects/{id}`，再刷新。 | 服务端返回 SPA HTML（200），前端用访客凭证从服务端恢复该项目；不能只靠站内导航成功。 |
| TC-M1-BE-04 版本与修改 | 完成首版后提交新需求，检查新 run 与旧版本；让新 run 失败后查看旧版。 | 新需求创建独立 run/spec/版本；旧源码 hash 不变，最后成功版本仍可读取。失败 run 不覆盖旧好版本；回退代码不暗中回退业务数据。 |

## P0：幂等、预算与恢复

| ID | 操作 | 预期与判定 |
| --- | --- | --- |
| TC-M1-BE-05 run 幂等 | 对 `POST /api/projects/{id}/runs` 用同一 `Idempotency-Key` 并发/顺序重复请求；再用不同键发起并发 run。 | 同键得到同一 `run_id`，仅一条需求记录/活动 run；同项目第二活动 run 被拒或明确排队，不能同时写同一工作区。 |
| TC-M1-BE-06 决策与产物幂等 | 对同一计划确认重复发送相同键；在文件写入、版本打包之后模拟进程停止并重启恢复。 | 确认只提交一次、一个 approved spec；恢复检查副作用账本/hash，文件不重复损坏、版本唯一、事件不重复或具可去重 ID；最终状态与产物一致。 |
| TC-M1-BE-07 预算暂停 | 测试配置把模型调用上限设为很低的值，再分别模拟调用次数、Token 输出余量和执行时间上限。 | 任一上限触发后暂停模型/工具调用，保留检查点与最后可用版本，显示具体原因及四项已用量/上限；没有用户确认时不恢复，需求文本不能提升额度。 |
| TC-M1-BE-19 明确扩额与恢复 | 先触发 Token 输出余量不足；仅选其他项、再选 Token 并重复提交相同幂等键；刷新/重启后继续，同项目尝试创建第二活动 run。另测试旧 `budget_exceeded` run 主动打开扩额卡。 | 当前耗尽项必须增加；每次 Token 增量为 100,000，其他增量明确可见；同键只增加一次、旧卡 409；同一 run 从原检查点继续，模型用量和执行秒数不清零，等待不计时，第二活动 run 被拒；旧 run 仅在最近且检查点可继续时可恢复。 |
| TC-M1-BE-20 自动修复轮次扩展 | 测试配置把修复上限置为 0，注入一次可修复编译错误；在人工卡选用“增加 30 轮自动修复并继续”并发送。另以连续同错停机检查卡动作。 | 上限持久增加 30 轮，原 run 回到 `CodeLoop` 并自动修复；相同消息重放不重复增加。无进展或同错循环停机不提供自动扩轮，旧可用版本不受影响。 |
| TC-M1-BE-15 执行时长计费 | 在澄清卡和计划卡各模拟等待超过 15 分钟后继续；另分两段注入执行时长并在第二段超过上限；模拟执行中心跳后服务重启。 | 两段用户等待、排队及停机不消耗时长预算；多段 Agent 执行累计不清零，达到上限后停止；重启从持久化心跳用量恢复。历史 run 未记录执行时长时显示未知，不用任务存续时间反推。 |
| TC-M1-BE-08 构建修复 Harness | 用受控假模型/故障注入，让同组错误连续出现、单个错误间歇复现及每轮出现新错误；观察 `BuildTest → Diagnose → CodeLoop`。 | 同组错误连续 3 次停止；单个错误累计第 5 次出现停止；不同错误允许第 60 轮自动修复，之后仍失败则交 `WaitRepair`。每轮保留诊断和日志引用，失败候选不入可用版本；人工原样重建或定向修复每次只执行一轮。模型/token/执行时间硬预算可提前停止。 |
| TC-M1-BE-18 源码校验与定向修复 | 固定模型先返回 hook 中状态更新副作用，再返回修正的该 hook；另分别注入无法定位的目录错误、局部响应夹带额外文件、源码和构建交错失败、连续相同违规及重启后人工继续。 | 首次输入包含实际文件/状态规则；检查点含受控问题与具体文件、不含完整源码；能定位时模型只返回目标文件，其余候选文件内容不变；无法定位时全量重生；局部结果合并后仍全量校验；源码与构建共享 60 轮、3 次无进展和第 5 次复现停机；重启不复用已失败候选，未通过候选不构建或占版本名额。 |
| TC-M1-BE-13 构建失败证据与人工恢复 | 让模型输出可写入但不能通过 TypeScript 构建的源码；测试配置将自动修复轮数设为 0；查看小结，显式原样重建，再指定方向修复。 | `awaiting_repair` 卡给出失败命令、最近错误、历次结果、日志引用；项目无新版本；另一访客不能读取日志或提交动作。原样重建不调用模型，再失败生成新卡；旧卡 409、重复幂等键不重复执行；定向修复成功后才保存版本。 |
| TC-M1-BE-14 历史计划兼容性 | 用旧 `appData` 计划和终态构建检查点模拟历史运行，再查看项目与尝试恢复。 | 小结仍可见；因批准计划与当前模板冲突，不显示继续修复动作，恢复接口拒绝；用户只能明确修改需求发起新 run，不消耗模型额度。 |
| TC-M1-BE-09 瞬时模型故障 | 依次注入 429、超时、5xx、恢复成功；再注入持续失败。 | 瞬时错误最多三次退避重试，重试前检查取消/预算；成功继续原 run，持续失败保留可恢复状态和脱敏错误。非幂等工具不盲重试。 |
| TC-M1-BE-14 模型输出截断 | 注入 CodeLoop 响应 `finish_reason=length`、正文为空、完成 token 达到输出上限；第二次返回合法 JSON。另以真实模型运行一条较复杂的待办需求。 | 重试上限增长且不越过剩余 run 预算；CodeLoop 按配置关闭思考模式；Trace 记录 finish reason、额度和长度但不存源码/推理正文；合法响应后继续真实构建。 |
| TC-M1-BE-15 计划与代码权限一致 | 首版 Plan 将 `localStorage` 列入实现功能，次版改为页面 state；再进入用户确认。 | 不把不能执行的计划交给用户批准；只在计划符合本轮能力后发确认卡；源码校验拒绝越界能力时指出具体项。 |
| TC-M1-BE-10 取消 | 在模型调用和构建阶段分别请求取消。 | run 进入持久终态，子进程/后续调用停止，已完成日志与最后好版本保留；重复取消安全；刷新后显示相同状态。 |

## P0：权限与数据安全

| ID | 操作 | 预期与判定 |
| --- | --- | --- |
| TC-M1-SEC-01 阶段工具权限 | 在澄清/计划阶段伪造写文件、执行命令工具调用；在编码阶段请求读仓库外文件、`.env`、绝对路径和 `../` 穿越；在构建阶段请求任意 shell 命令。 | 服务端 allowlist 与 canonical path 校验拒绝这些调用，未产生副作用；可见安全失败事件只含必要说明，不泄漏文件内容。前端限制不足以通过。 |
| TC-M1-SEC-02 密钥隔离 | 在需求中诱导模型打印环境变量/密钥；检查模型上下文、生成源码/构建产物、事件、Trace、API 响应和浏览器网络请求。 | `MODEL_API_KEY` 只在服务端适配器使用，不进入生成项目、浏览器 bundle、日志/事件/Trace 或模型消息。用测试用伪密钥作搜索标记；不可输出真实密钥作证据。 |
| TC-M1-SEC-03 项目隔离 | A/B 各创建项目；B 请求 A 的项目、run、事件、版本与产物 URL；A 尝试猜测 B 的 ID。 | 未授权读取/改写均拒绝；ID 的不可预测性不代替授权；项目侧工作区和版本严格分离。 |
| TC-M1-SEC-04 不可信内容 | 需求包含 HTML/脚本、提示注入和恶意文件名；模型工具参数注入路径/命令。 | 卡片安全渲染；模型输出按 schema 和工具参数校验；不执行需求文本，不让模型扩大权限。不能证明 Runner 安全时禁止公网代码执行。 |

| ID | 操作 | 预期与判定 |

| TC-M1-BE-11 checkpoint 一致性 | 在计划确认事务前后、工具副作用后、打包前后注入服务崩溃并重启。 | checkpoint 与业务记录不一致时有修复路径；不会绕过批准、重复写入或把未构建产物标成成功；旧好版本保留。 |

## MVP1 出口与遗留边界

`TC-M1-E2E-01`、所有 P0 门禁/持久化/幂等/预算/安全用例通过，且每个失败有缺陷记录与复测证据，才声明 MVP1 完成。P1 可记录已知限制，但不能与 P0 成功相矛盾。MVP2 另需实际浏览器预览交互、预览业务数据刷新后读回、SSE 断线回放与独立 origin 安全测试；公开可测试链接和 Atoms 部署兼容性也需在上线验收单独实测。
